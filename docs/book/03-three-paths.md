# 第 3 章 · 三条路径：写入、检索、展示

上一章的图是静的。这一章让三条真实的路径穿过它。

三条路径共用一张图，但走的是不同的边。看完你会发现它们交在同一个点上——那个点是下一章的主题。

每条路径这里只走骨架，不进任何一个部件内部。**目标是贯通，不是深入。**

---

## 路径一 · 写入：从别人的文件到你的索引

起点是一个你不拥有的文件。Claude Code 在 `~/.claude/projects/<project>/<sessionId>.jsonl` 里追加了几行；或者 Codex 在 `~/.codex/sessions/2026/08/04/` 下落了个新文件；或者 Kimi 在某个 session 目录里改了 `wire.jsonl`。

```text
① 发现（discover）
   适配器扫自己的根目录，对比"上次处理到哪儿"的游标，
   列出需要重新索引的工作单元 IndexUnit。

② 解析（parse）
   针对一个单元，适配器从游标处恢复，产出一串 canonical record。
   这是个生成器：一边产出记录，最后 return 新游标。

③ 落库（persist）
   persist 消费这串记录，按 kind 分派成 SQL，写进注入的数据库 handle。
   生成器 return 的新游标，也在同一个事务里写进 index_state。

④ 收尾（finalize）
   全部单元处理完，一个事务内：回填 project_path、重建 FTS 索引、写时间戳标记。
```

四个环节里最值得注意的是**边界在哪儿**：

```text
适配器                  persist
━━━━━━━━━━━━━━━      ━━━━━━━━━━━━━━
知道 JSONL 长什么样    不知道来源是谁
知道怎么去重           不知道文件在哪
知道游标怎么编码       原样存游标，不解释
从不打开数据库         唯一打开数据库的
        └──── TranscriptRecord ────┘
                （共同语言）
```

游标这件事是个好例子。适配器返回一个字符串，编排层原样存进 `index_state`，下次原样递回去——**中间没有任何人解释它的含义**。Claude 用它编码"文件 mtime + 已处理行数"，Kimi 用它编码"整个目录的聚合 mtime + 总行数"。两种含义完全不同，但对存储它的那一层来说毫无区别。

一个单元一个事务。某个文件解析失败，记下来跳过，不影响其他文件——但收尾那一步失败不被吞掉，因为半完成的收尾会让索引处于不一致状态。

**这条路径有两种触发方式**：桌面 App 在跑的时候，它监听文件变化持续索引（daemon 模式）；没有 App 的时候，每次 CLI 调用顺手把索引推到最新（被动拉取模式）。两种模式走的是**同一套代码**，区别只在谁触发、以及谁有资格写。第 13 章讲后者。

## 路径二 · 检索：从一句提问到一份 JSON

起点是你敲下的一句话：

```text
/obelisk 上次那个 auth bug 最后到底改了哪些文件
```

```text
① skill 层
   纯文档的 skill 指引 agent：先 overview() 拿地图，
   把中文问题翻成英文检索意图，同时问记忆层和证据层。
   agent 把这些写成一小段 JS，落到临时文件。

② CLI
   obelisk --query /tmp/q.mjs
   读文件 → 交给 Core → 结果 JSON 打到 stdout。全程不含检索逻辑。

③ 刷新索引
   executeQuery() 第一句是 buildIndex()。
   ——就是路径一。检索顺手把写入路径跑了一遍。

④ 只读连接
   openReadDb()：readOnly 打开，不建表、不迁移、不设 PRAGMA。

⑤ 沙箱
   node:vm 新上下文，脚本被包成异步 IIFE，30 秒超时。
   白名单里有 16 个 helper 和一批内置对象——
   没有 require、没有 fs、没有 fetch、没有 process。

⑥ 执行
   helper 走 FTS5 和结构化 JOIN，在数据这一侧完成过滤和裁剪。

⑦ 返回
   脚本 return 的值序列化成 JSON。agent 读它，可能再追一轮，
   最后用自然语言回答，并带上可核对的 ID。
```

两处值得停一下。

**第 ③ 步意味着两条路径是嵌套的，不是并列的。** 没有"同步"这个独立动作——索引新鲜度是查询的副作用。三个动词（`search`、`query`、`attune`）的入口第一句都是 `buildIndex()`。

**第 ⑤ 步的白名单决定了脚本的能力边界：能读，但带不走。** 沙箱里没有任何 I/O，脚本唯一能产出的东西就是它的返回值。这不是防恶意——脚本是 agent 自己写的——而是把"查询"这个动作钉死成一个纯函数。

一段真实的查询脚本长这样：

```js
const map = overview({ limit: 6 });
const project = map.current.project?.project;

return {
  prior_memories: memories({ project, query: 'authentication bug fix', limit: 5 }),
  evidence: search('auth bug fix', { project, limit: 8 }).map(h => ({
    session_id: h.session.id,
    uuid: h.message.uuid,
    snippet: h.message.text?.slice(0, 240),
  })),
};
```

注意最后那个 `.map()`：**裁剪发生在本地，只有 240 字的片段和可继续追查的 ID 回到 agent 的上下文。** 这是"写脚本"相对于"调一组检索工具"最实际的好处——过滤在数据这一侧，不在 context 里。

## 路径三 · 展示：从索引到人眼

起点是你在桌面 App 里点开一个 session。

```text
① 取快照
   主进程按 session_id 从 SQLite 拉六张表：
   messages / toolCalls / toolResults / subagents / workflows / summaries

② 组装
   assembleSessionDetail(snapshot)
   → 把散在六张表里的行，重新组装成一条可读的时间线：
     工具调用和它的结果配对、subagent 挂到发起它的调用上、
     workflow 挂到它的父调用上。

③ IPC
   组装结果通过 preload 送到渲染进程。

④ 渲染
   Vue 把时间线画成卡片：diff、终端输出、文件查看器……

⑤ 实时更新
   session 还在进行时，重新取快照、算出与上一版的差异（按表按主键），
   只把增量补丁送过去，而不是整份重传。
```

这条路径上有一件事必须点明，因为它是整个架构的关键测试点：

**`assembleSessionDetail` 从不检查 `source`。**

它拿到的六张表里的行，可能来自 Claude、Codex 或 Kimi，但它一次都不问"这是哪来的"。它只做确定性的排序、分组和配对。

这做得到，是因为**所有来源特有的语义，在路径一的第 ② 步就已经被适配器消化掉了**。哪条消息该显示、哪条是注入的传输上下文、哪个工具调用属于哪个 subagent——这些判断全都在适配器里做完，以显式字段的形式写进记录。展示层不需要猜，也不允许猜。

还有一个细节：`assembleSessionDetail` 有**两个可能的输入**。它可以吃从 SQLite 查回来的行，也可以直接吃适配器一次全新解析产出的记录流——因为两者说的是同一种语言。这个性质让"数据库里的东西"和"直接解析出来的东西"可以互相校验，而不会各自漂移。

## 三条路径，一个交点

把三条路径叠在一起：

```text
        外部 JSONL / 目录
               ↓
        ┌─────────────┐
        │  适配器解析  │  路径一
        └─────────────┘
               ↓
      ╔═══════════════════╗
      ║ TranscriptRecord  ║   ←──── 三条路径都经过这里
      ╚═══════════════════╝
          ↓            ↓
    ┌──────────┐  ┌──────────────┐
    │ persist  │  │ session-detail│  路径三
    └──────────┘  └──────────────┘
          ↓            ↑
      ┌────────────────┘
      │  SQLite
      ↓
  ┌─────────┐
  │ 检索helper│  路径二
  └─────────┘
```

写入路径**产出**它。展示路径**消费**它——直接消费，或者经过 SQLite 往返之后消费。检索路径消费的是它的序列化结果。

三条路径，一个共同语言。这个交点承受着系统里所有的差异：上游 N 种转写格式、下游两种数据库 binding、两个消费者、两种索引模式。它们全被压在这一个类型定义的两侧。

**这个点凭什么划在这里？** 下一章。

## 这一章你应该带走的

1. 三条路径：写入（发现→解析→落库→收尾）、检索（嵌套了写入）、展示（快照→组装→渲染）。
2. 检索路径每次都会先跑一遍写入路径——没有独立的同步动作。
3. 展示层从不检查来源，因为来源语义在解析时就被消化掉了。
4. 三条路径全部穿过 `TranscriptRecord`。
