# 第 15 章 · 扩展与边界

最后一章分两半：**怎么在这套架构上加东西**，以及**这套架构现在已知的问题**。

第二半更重要。一本只讲"哪里做对了"的书是宣传册；讲清楚"现在知道哪里还不对"才是架构书。

## 上半：加一个来源

假设要接入一个新的 coding agent，它的转写存在某个目录里。完整的工作量是这样。

### 要改的：两个文件

**一、新建 `packages/core/src/providers/<name>.ts`**，实现六个成员（第 6 章）：

```ts
export function createFooProvider({ rootDir = defaultFooRoot() } = {}): ProviderAdapter {
  return {
    name: 'foo',
    descriptor: { id: 'foo', name: 'Foo Code', vendor: '...', defaultRoot: rootDir, color: '#...' },
    indexVersionMarker: '__foo_canonical_transcript_v1__',
    watchRoots: (configuredRoot) => [join(configuredRoot, 'sessions')],
    discover: (ctx) => discoverAt(rootDir, ctx),
    parse,
    raw: (input) => rawFoo(rootDir, input),
  };
}
```

**二、在 `builtins.ts` 里加一行**（那个文件一共 14 行）：

```ts
return createProviderRegistry([
  createClaudeProvider({ rootDir: roots['claude'] }),
  createCodexProvider({ rootDir: roots['codex'] }),
  createKimiProvider({ rootDir: roots['kimi'] }),
  createFooProvider({ rootDir: roots['foo'] }),      // ← 新增
]);
```

### 不用改的：全部其他地方

```text
schema.sql            不动
persist.ts            不动
session-detail.ts     不动
query.ts 的 16 个 helper  不动
indexer.ts / provider-indexing.ts   不动
CLI                   不动
App 主进程 / 渲染进程  不动
```

**这不是理论承诺，是第 7 章那次验证的结论。** Kimi 是一个数据模型和前两个完全不同的来源（目录型、操作日志、带撤回），接入时的硬约束就是"不改 schema、不加 record 类型"，而它做到了。

`descriptor` 里那个 `color` 会自动出现在 App 的设置界面和来源色块上——因为渲染层消费的是 `registry.catalog()`，不是一个硬编码的列表。

### 三个必须先回答的设计问题

写代码之前，这三个问题决定了整个适配器的形状：

**问题一：什么是一个 `IndexUnit`？**

一个文件？一个目录？数据库里的一段？

判据是：**处理它的时候，需要看到的东西是否都在这个单元里。** Kimi 之所以必须以目录为单元，是因为主 agent 和子 agent 的 wire 文件必须一起看（第 7 章）。

**问题二：游标编码什么？**

必须能回答两个不同的问题：discover 用它判断"变了没"，parse 用它决定"从哪儿接着读"（如果是增量的话）。

现有的三个都是 `"数字:数字"`——这是当前编排层的实际约束（第 6 章那个折扣）。

**问题三：增量还是全量？**

关键判据是：**解析某一部分时，是否需要看到其他部分？**

```text
需要跨行的双向视野    → 必须全量（Codex 的去重）
有撤回/删除语义       → 必须全量（Kimi 的 undo）
纯追加、逐行独立      → 可以增量（Claude）
```

选定之后，`countMode` 跟着定：增量报 `'delta'`，全量报 `'total'`。

### 语义映射

然后是把源格式映射到十种记录上。这一步没有捷径，但有一个检查清单——**每一项都要问"我的来源里，这个概念对应什么"**：

| 记录 | 要回答的问题 |
|---|---|
| `session` | 一次会话的边界在哪？标题从哪来？ |
| `message` | 哪些是真实对话？哪些是注入的传输上下文（→ `visibility: 'hidden'`）？ |
| `tool_call` / `tool_result` | 怎么配对？调用 ID 稳定吗？ |
| `subagent` | 有子 agent 概念吗？它和父会话怎么关联？ |
| `summary` | 有压缩/摘要事件吗？ |
| `workflow` / `workflow_agent` | 通常没有——留空即可 |
| `message-turn-duration` | 耗时信息在哪条记录里？ |
| `delete-session` | 有撤回、undo、内部线程需要隐藏吗？ |

**没有的概念就不产出。** Codex 没有 workflow，那两张表对它就是空的。

### 六个容易踩的坑

1. **ID 必须带来源前缀**（`foo:<id>`），否则会和别的来源撞（第 5 章）。
2. **不能 import `node:sqlite`**，也不能让 `parsing.ts` 引入它——App 会在运行时炸（第 2、6 章）。
3. **`visibility` 要自己判断完**，不能留给展示层猜（第 4、12 章）。
4. **不能假设单元的处理顺序**，一行可能由多个单元拼成，不知道的字段就别写（第 6、8 章）。
5. **`raw()` 要能定位到原始行**，因为索引文本被截断到 10k（第 6 章）。
6. **改了解析语义就升版本标记**，否则老数据不会被重放（第 14 章）。

### 判断标准：什么时候该改中间那层

绝大多数需求不需要动 canonical record。判断方法：

```text
新来源有一个我们没有的概念
  ├─ 能不能映射到已有记录？        → 能就映射（Codex 子线程 → subagent）
  ├─ 能不能表达成已有记录的组合？   → 能就组合（Kimi 全量替换 = delete-session + 重建）
  └─ 都不行，且这个概念对多个来源普遍存在  → 才考虑加记录类型或字段
```

第三条的门槛里，"**对多个来源普遍存在**"是关键。一个只有某个来源才有的概念，加进共同语言就是把私有细节泄漏给所有消费者。

## 下半：已知的边界

按"多容易出问题"排序。

### 一、没有类型保护的约束

这三条最危险，因为**违反它们不会有编译错误**：

**`parsing.ts` 和所有适配器必须 SQLite-free。** 加一行 `import { DatabaseSync } from 'node:sqlite'`，CLI 侧一切正常，App 侧在运行时崩。测试如果不覆盖 Electron 环境，也发现不了。

**`messages` 的 upsert 不能包含 `turn_duration_ms`。** 第 8 章讲过：往那个列清单里手滑加上它，Codex 和 Kimi 每次全量重解析都会清掉耗时数据。而且不会报错，只是数据莫名其妙地丢。

**`fullReindex` 时必须把 `changedPaths` 设为 `undefined`。** 漏了它，一次本该完整的重放会静默退化成增量更新。

这三条现在靠注释和人的记忆维持。**它们是这份代码里最脆的地方。**

### 二、抽象上的折扣

**游标声称不透明，实际上被假设为一对数字。** 因为编排层要把它拆进 `index_state` 的两个数值列（第 6 章）。一个需要别的形状的来源（比如一个 opaque 的 base64 水位）会撞上这里。

**`index_state` 被当键值存储用。** 列名叫 `jsonl_path`，存的却是 `__app_heartbeat__`；列名叫 `mtime`，存的却是心跳时间戳（第 5 章）。务实，但读代码时得靠约定认出来。

**`is_meta` 和 `visibility` 并存。** 后者是对前者的修正（第 4 章的「当时」），但前者没有被移除——因为它已经被查询层和 skill 文档广泛依赖。两个字段各自有明确职责，但这个组合仍然带着历史包袱。

**`search()` 返回的 `context` 和 `context(uuid)` 不是一回事**（第 10 章）。命名重叠，靠文档区分。

### 三、有意的取舍

这些不是缺陷，但值得知道代价：

**索引文本截断到 10k。** 换来的是索引体积可控，代价是全文必须回源文件（`raw()`）。如果源文件被删了，超出 10k 的部分就真的没了——这正是 trajectory 那条路线要解决的问题（见下）。

**记忆层强制英文。** 换来跨语言召回的一致性，代价是记忆内容和用户的工作语言可能不一致（第 11 章）。

**单写者模型。** 换来的是简单和安全，代价是并发写入的吞吐上限。对一个本地索引来说这不是瓶颈，但它是一个明确的天花板（第 13 章）。

**`schema.sql` 与 `sqlite_master` 必然漂移。** 老库的列顺序和建库脚本不同（第 5 章实测过）。无害，但要求所有代码按列名访问。

### 四、只能靠人解决的两种情况

第 14 章那张自愈表里的两行：

- **幽灵行**——源文件被删除后留下的孤立数据，增量索引表达不了"这个东西不在了"，只能 force rebuild。
- **索引文件损坏**——同上。

## 尚未完成的方向

### MCP transport

第 1 章说过四个动词是唯一的公共面，CLI 只是其中一个 transport。MCP server 是已经规划好的第二个：同样的四个动词、同样的 Core，只是把脚本以字符串而不是文件路径传进来。

**契约已经为它留好了位置。** 第 10 章那句"helper 从不被提升为对外的工具"，防的就是 MCP 实现时把 16 个 helper 摊成 16 个 tool——那会让 Obelisk 从记忆运行时退化成普通检索插件。

### Trajectory：把可移植的 JSONL 放到 SQLite 上游

这是一个已经写完设计、尚未实现的方向（`docs/trajectory-v0-design.md`，2026-07-29）。它值得放在最后一章，因为**它会修改这本书第 1 章的一条前提**。

现在的链路是：

```text
外部 JSONL ──→ 适配器 ──→ SQLite
```

设计中的链路是：

```text
外部 JSONL
    │  适配器解析
    ▼
Obelisk trajectory JSONL        ← 唯一事实层，持久化，可迁移
    │
    ├─→ Obelisk SQLite          （检索索引，10k 截断在这一层发生）
    ├─→ 其他格式的导出
    └─→ 第三方 memory / query 系统
```

**这不是加一层缓存，是一次定位变更。** 设计文档把它写成一个显式决定：

> 此前记录的定位是：**canonical index over foreign logs**——Obelisk 永不拥有源日志……
> **v0 改变这一点。** trajectory 自己持久化，并且可以被单独转移、在另一台机器上加载进 Obelisk。

后果是对称的：

```text
得到   可迁移、可重放、不依赖 harness 是否还在
       源日志变成可删除的（这正是价值所在，不是副作用）
失去   「Obelisk 只是一层索引，删了也不损失什么」这个轻量性质
```

**第 1 章那条边界"不拥有源日志"，在这个方向下会失效。** 所以设计文档特别强调"这条必须是显式决定，不能顺手滑过去"。

核心不变量写得很干净：

> `foreign JSONL → trajectory → SQLite` 的入库结果，必须等于 `trajectory 文件 → SQLite`。

这是"把文件递给别人，对方就能加载这个 session"的形式化表述。

值得注意的是它对现有架构的态度——**schema 不动**。设计里那条"每个看起来需要加列的缺口，都在 trajectory 层的解析时解决"，意味着改动的爆炸半径是**代码而不是数据**。这和第 14 章那个"重放取代迁移"的思路是一致的。

顺带一提，这个设计里有条方法论值得单独抄下来：

> reading source proves a path can execute, not that it does; measure before grading a gap.

**读源码只能证明某条路径可以执行，不能证明它真的在执行。** 那份设计里几个原本被判为阻塞的缺口，实测之后一个被降级（0.085% 的歧义行）、一个被撤销（那条代码路径实际是死的）。

## 全书收束：五个原则

回头看，这套架构反复应用的是同样几条判断。它们不限于这个项目。

### 一、把差异压在一个点的两侧

上游 N 种格式、下游 M 个消费者，成本可以是 N × M，也可以是 N + M。区别只在于有没有一个中间语言，以及**这个语言是不是没有人可以绕过**。

第 2 章那三条依赖规则（适配器不碰数据库、persist 不认来源、外壳不实现检索）就是"没有人可以绕过"的具体形式。

### 二、接缝划在语义完整、序列化未发生的那一层

往下一层，语义被压扁，消费者只能猜；往上一层，格式没被消化，每个消费者都得懂全部来源。

判断一个接缝划得对不对，最实用的方法是想清楚**它划在别处会怎样**（第 4 章）。

### 三、让抽象承接差异，而不是消灭差异

`countMode` 的存在是因为三个适配器对增量的理解根本不同。与其让 persist 去猜（那就要认 source），不如让适配器明说。

**好的共同语言不是"大家都一样"，是"差异可以被表达"**（第 7 章）。

### 四、投影可以扔掉重建，判断不行

`memories` 是这个系统里唯一算不出来的东西，所以它从不参与任何重建。**正因为最坏情况下的损失有界，才敢把"清空重建"做成一个用户随手能点的按钮**（第 5、11、14 章）。

### 五、不确定时选择少做

事务状态问不出来就当作还活着；所有权读不到就当作别人可能在写；只有确认事务已结束才重试。

因为失败代价不对称：**漏掉一次索引，下次会补上；两个进程同时写，可能损坏索引**（第 13 章）。

## 最后

这本书细读的部分大约七千行：Core 四千七、CLI 七十一行、App 主进程与共享层两千三。加上被明确划出范围的渲染层和 skill 文档，整个产品两万行出头，另有近一万行测试。

分量集中在 Core，而 Core 里真正定义形状的是 `providers/types.ts` 那两百多行——**没有一行运行代码**。

它不大，但它被三种范式各异的数据源、两种 SQLite binding、两个使用面、五种并发写者各撑过一遍，中间那层共同语言一个字没改。

**如果你只带走一件事，带走这个：那层语言不是设计出来的，是被证伪出来的。** 第一版 ADR 说"一个 parse core + 两个 persist layer"，两个轴都错了；`visibility` 是被一个显示 bug 逼出来的；`delete-session` 的最强用法（幂等整体替换）超出了它的设计意图。

架构的质量不体现在第一版有多漂亮，而体现在**它被推翻的时候，改动的半径有多小**。
