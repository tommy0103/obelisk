# ADR-0009：Obelisk 作为 DeepSeek Harness 的可选历史检索插件

> Mount Obelisk as an opt-in second retrieval channel in DeepSeek Harness,
> coexisting with its built-in session-history search. This is "Mode 0" of the
> three integration options discussed.

Status: **Accepted — 2026-08-14**

## 一句话提案

把 Obelisk 作为**可选的第二检索通道**接入 DeepSeek Harness（下称 DSH），与
DSH 自带的会话检索**并存**，不改动双方现有核心。不启用时，DSH 的行为与今天
完全一致；启用后，模型多一个入口，能查询"其它工具的历史"和"此前存下来的
结论"。

（"插件"约等于给编辑器装一个扩展：不装不影响原功能，装了多一个入口。）

## 背景：两个事实，各管一段

先解释"检索通道"：模型（AI）干活时会调用一些查询工具来找资料。DSH 今天给
它配了一套查"自己历史"的工具；本方案是再加一套查"Obelisk 档案"的工具。

**事实一：DSH 自带的检索只查它自己。** 它能实时、精确地查同一工具内、同一
项目目录下的历史会话，但看不到别的工具（如 Claude Code）里发生过什么，也
没有"记住结论"的概念——每次都是现查原始记录。

**事实二：Obelisk 管的是整台机器的历史。** 它把多个编码工具的会话归档进一个
本地档案库，外加一层"持久记忆"：人可以审批地记录结论（例如"上次为什么选 A
而不选 B"），随时可查、可撤回。

一句话概括：DSH 的检索管"这间屋"，Obelisk 管"整栋楼"。两者不冲突，缺的只是
把"整栋楼的档案"递到 DSH 的模型手边。

## 方案：并排双通道，各查各的

四个设计原则，每条附一段"为什么"。

1. **并存，不替代。** DSH 自带检索原样保留、默认启用；Obelisk 通道默认关闭、
   按需启用。
   *为什么*：DSH 自带检索的强项是"实时查正在进行的会话"，这是 Obelisk 的归档
   式索引给不了的；反过来，跨工具语料和记忆层也只有 Obelisk 有。让两个通道各
   管一段，比让谁吃掉谁都便宜、都安全。

2. **零耦合：双方核心代码都不动。** 只在 DSH 一侧加一个很薄的插件——约等于
   "一个工具入口 + 一段说明书"——把模型的提问转成 Obelisk 现成的查询命令，
   把结果转回模型能读的文本。
   *为什么*：改动最小就是风险最小；任一方日后升级，这层薄转接几乎不用跟着改。
   DSH 已经预留了这类扩展接口（它的自带检索本身就是以同样方式挂上去的），
   Obelisk 也已经有成熟的命令行查询入口——两头都是现成的。

3. **复用 Obelisk 已有的"身份"。** Obelisk 今天就是以"命令行工具 + 技能说明"
   的形式被 Claude Code、Codex 等工具使用的；DSH 只是再当一名宿主，不做任何
   特殊待遇。
   *为什么*：不用为 DSH 新造一套查询界面。Obelisk 积累的查询习惯——先看全局
   地图、再查证据、必要时深挖——原样继承，且多个宿主共享同一套行为，未来维护
   只有一处。

4. **沿用 DSH 已有的安全与体验纪律。** DSH 自带检索已经立了规矩：结果数量
   封顶、查询限时、不把底层技术细节暴露给模型。Obelisk 通道照抄同一套。
   *为什么*：模型眼里两个通道手感一致；安全边界不必重新发明，评审也只需审
   一次。

## 装上之后，体验变化

今天，在 DSH 里问"我们之前怎么修过这个 bug"，模型只能搜 DSH 自己的历史，
Claude Code 里干过的事它答不上来。装上之后，同一句话可以命中所有工具的历史，
还能命中此前存过的结论；结论背后带着"证据在哪条会话、哪条消息"，可以一路
追溯，而不是一段没有出处的摘要。

"说明书"（每次请求随附给模型的固定说明，教它何时用哪个工具）会写清分工：
查本工具近期的会话用 A 套工具，查其它工具的历史与记忆用 B 套工具——避免两套
工具抢活干。

## 需要说清的三个边界（评审重点）

1. **新鲜度：归档，不是实时。** Obelisk 是定期拍快照式的档案，刚结束的对话
   要等下一轮归档后才能被查到。想查"刚才发生的事"，仍走 DSH 自带通道——两个
   通道的分工正好因此成立。
2. **可见范围：全机器 vs 单项目。** DSH 自带检索有"只能查同一项目目录"的
   规矩；Obelisk 档案天然是全机器的、跨项目的。已拍板：先全量可见（见"拍板
   结果"第 2 题）。
3. **查询手感：固定按钮 vs 自由编写。** DSH 自带检索是固定几个按钮式的；
   Obelisk 通道允许模型写小程序去查（程序关在沙箱里，只读档案、碰不到别的
   文件）。灵活性更高，输出形态略有不同，说明书需要把分工讲清楚。

另有一个实现期要验证的小点，不影响本方案取舍：Obelisk 的档案库同一时间只
允许一个进程写入。若桌面 App 正开着，命令行查询如何配合需在实现时确认
（排队或换一种访问方式均可）。

## 明确不做（挂起）

"让 Obelisk 取代 DSH 自带的检索引擎"——挂起。理由一句话：DSH 自带的实时性是
Obelisk 的归档模型替代不了的，硬替等于丢掉两者各自的强项。将来若出现真实
需求（比如想在 DSH 里直接命中 Claude Code 的会话），再评估"把 DSH 自己的会话
日志也接进 Obelisk 档案"这条路线；现在不预先开发。

## 改动分工

| 侧 | 改什么 | 量级 |
|---|---|---|
| DSH | 新增一个可选小插件（默认不装）：注入 skill + 工具入口 + 说明书文案 | 小；核心零改动 |
| Obelisk | 核心零改动（按项目过滤留作后续增强，本次不开发） | 无 |
| 两边文档 | 各加一节说明 | 小 |

实现路径按拍板结果执行：注入 skill 与工具——skill 保持原样（不改变模型对
Obelisk 本身的理解），工具负责执行查询；其余是 DSH 插件规格层面的适配。

## 拍板结果

（答复为评审人原文。）

1. **定位**：是否认可"并存互补、不做替代"？
   答复：认可
2. **可见范围**：Obelisk 通道默认全量可见，还是按项目目录过滤？前者最省事；
   后者更贴近 DSH 现有安全习惯，需要给 Obelisk 补一个小功能。（我的倾向：先
   全量可见上线，过滤作为紧随其后的增强——档案是本机个人历史，不是共享数据。）
   答复：先全量可见，这和 obelisk 在别的 Agent harness 下的表现一致。对于 dsh 来说，obelisk plugin 可以做得非常轻量，因为事实上只是注入 skill 和工具即可。剩下的是插件规格层面的适配。
3. **记忆写入**：Obelisk 的"记住结论"操作，在 DSH 里是否同样保持"模型提议、
   人来批准"？（推荐：是，与其它宿主一致。）
   答复：确认指 obelisk 的记忆层（remember/forget 及 `--attune` 审批流程）。
   答复（评审人原文）：你说的是 obelisk memory 吗？如果是，应该是的。但是我不
   认为这是需要拍板决策的，理由同 2。我们不应该改变 Agent 本身对于 obelisk
   的理解。最多只允许轻量的对于 1 的变动的补充。
   结论：记忆流程为 obelisk 既有契约的直接继承，随 skill 原样带入 DSH，无需
   单独决策；不改变模型对 obelisk 的既有理解。
4. **启用方式**：插件默认关闭、由部署方显式启用？（推荐：是。）
   答复：是

## 前端呈现（补充拍板，2026-08-14）

**需求**：obelisk 调用在 DSH 前端渲染成独特样式，让人更容易意识到 obelisk
被调用了；底层 session 记录保持不变，只是展示层的变化。

**机制**：DSH 客户端插件系统支持"双面包"（`dsh.client` 声明 + `./client`
导出）：宿主 Loader 加载插件行时，把包内置的 `lib/client.js` 喂给浏览器
插件表；浏览器侧通过 slot 注册表按线上工具名接管渲染。因此**前端贡献由
obelisk 插件自己携带**，DSH 仓库无需改动。

**本轮范围（已实现）**：插件声明 `dsh.client`（platform: web），浏览器半边
注册 `obelisk_query` 工具名（第一方工具，键无冲突）的专属卡片：方尖碑
图符 + "Obelisk" 标签 + 有界查询摘要 + 可展开的 QUERY/RESULT 分区，主题
色走 DSW alias token。

**三条不变式**（本轮的核心约束）：

1. **模型面不变**：浏览器半边只存在于浏览器；模型看到的工具 schema、
   引导文案、结果文本与未装样式时完全一致，Agent 不会感知到任何区别。
2. **会话记录不变**：调用仍然记录为普通的 `obelisk_query` 事件；样式是
   浏览器对同一份冻结调用切片的投影，从不写回会话。
3. **只认领自己的键**：只注册 `obelisk_query` 一个线上工具名，其它任何
   工具的渲染不受影响。

**挂起：bash 路径的识别**。经 skill 直接以 Bash 命令调用的 obelisk
（`obelisk --query /tmp/q.mjs`）暂保持 DSH 原生 Bash 行渲染。原因有二：
(1) 工具视图槽按线上工具名"全有或全无"地接管，没有条件认领语义；(2)
客户端 bundle 的纯度门禁止跨插件复用 DSH 自带 Bash 行，整体接管意味着
obelisk 要重实现全部 bash 渲染并长期追随其演进。**后续路线**（记作上游
提案）：给 DSH 的 keyed 槽注册增加通用 `select` 谓词（chain 槽已有同款
语义，约十几行），obelisk 即可注册"命令以 `obelisk` 开头才认领"的条件
接管——命中时用专属样式，未命中时仍走 DSH 原行。该能力属于 DSH 仓库，
待有权限或上游接纳后再启用；届时本 ADR 追加修订记录。
